# 本机权限与授权复用

扫描先使用当前用户权限。普通文件、系统缓存、Snapper 快照清单或其大小计量遇到权限不足时，Linux 公共权限服务才申请只读授权。
系统缓存重试保留普通用户发现的包缓存、coredump 或 Go 路径，不在管理员环境重新运行 Go 环境发现；
Go 路径用原生字节传递，恢复权限后绑定目录与父目录身份，越过链接或嵌套挂载的计量不会当作完整大小。
后续检查复用仍存活的 helper 连接，每个请求单独校验来源、范围、协议版本、有效期与一次性 nonce。文件读取权限不等于删除确认。

Snapper 清单命令失败时，使用固定 system bus 上的 `GetConfig`（配置级）或 `ListConfigs` 核对实际访问结果。
只根据服务的结构化权限错误名或原生 IO 错误申请授权，不再从英文错误文字推断。诊断最多 5 秒并继承原取消/期限；
配置不存在、服务不可用或自定义程序输出权限文字都不会凭文字触发授权。成功的清单查询、保护状态和清理选择规则保持原语义。

图形宿主使用系统授权窗口；终端优先复用 sudo 认证，需要时才由 sudo 询问。SpacePrune 不保存或接收密码。
Linux 扫描窗口会说明“为完成扫描，请授权 SpacePrune 读取受保护位置的文件信息。本次授权不会删除文件。”；
清理窗口会说明“请授权 SpacePrune 清理你已选择并确认的受保护项目。”。这段用途说明跟随 CLI / App 的有效语言，
手动选择优先于系统语言，目前支持简体中文与英文，其他语言回退英文。窗口标题、密码标签和按钮仍由系统认证代理翻译。
首次安装或更新权限组件时，系统可能先显示通用安装认证；设置页保留本地化的组件安装说明。
自动准备完成后直接继续读取，不再额外询问一次。
非交互运行只使用现有连接或系统允许的非交互认证，无法授权时保留可读扫描结果并报告需要授权。
同次操作明确拒绝后不会因切换目录或 Snapper 配置再次弹窗。重新发起操作可重新申请；连接闲置 15 分钟或进程退出后失效。

授权复用还绑定本机 OS 登录身份，而不只按用户名或 UID 缓存。前台和终端绑定在用户切出、退出、
登录服务失效时单向撤销：取消在途特权请求，等待 native 连接停止，并拒绝旧 operation ID/generation
重新授权。处于退出中的登录也会撤销复用，不等待所有残余进程结束。
切回原用户不会恢复旧操作；新操作重新验证登录状态并按实际需要授权。普通无需权限的
文件扫描不因此要求图形登录。关闭失败仍保留首次结果，不能因连接已经移出缓存而显示成功。

独立非交互任务保持原运行条件：OS 能识别登录会话时仍绑定该身份并监视退出，但不因 GUI 切换
单独停止；只能使用它原本可用的非交互能力。已有前台绑定不会因调用者改成 NonInteractive 而降级，
后台绑定转为交互请求时先关闭旧连接并重新确认前台状态。OS 确证没有登录会话或登录服务的环境
使用进程作用域；已知登录监视失败不会静默降级。Linux 从可信 system bus 查询 logind，前台
user-manager 应用可通过同 UID 的 `User.Display` 关联会话，不信任 `XDG_SESSION_ID` 或 `DBUS_*` 身份提示。

Linux 读取和清理是两个独立组件，分别提供 metadata 与已确认清理计划的执行能力，不能互换启动协议。
CLI 与 Desktop 共用 Core 安装器管理的 `/usr/libexec/spaceprune/native-6-4`；数字对应读取协议 6 和清理协议 4。
文件和完整目录链归 root 持有且普通用户不可写，启动前同时核对 manifest 中的 SHA-256、角色协议和内置 Handler 契约。
传输协议相同并不代表 Handler 兼容：仍使用旧 Snapper 标识的组件不能显示为就绪，也不会被重新安装。
Go 原生捕获的功能探针只用于 Go worker 查找和实际进入提权的 Go 批次；Snapper、普通文件和系统缓存仍按各自原协议检查，
不会因为 helper 未实现 Go 新功能而不可用。混合方案中，Go 已由普通 worker 完成或不申请提权，不增加其他批次的组件要求。
若先复用基础旧会话、后续才有 Go 批次需要提权，会先准备匹配组件，确认旧连接关闭后再启动升级连接；已消费选择、
原操作期限和授权缓存保留。缺少 Go 随包组件不会封死后续 Snapper 批次，旧 helper 也不会接收 Go 选择。


```sh
cargo build --locked --release -p spaceprune-cli -p spaceprune-readonly-helper
./target/release/spaceprune authorization install
```

发行包携带相邻的 `spaceprune-readonly-helper`、`spaceprune-cleanup-helper` 和 `spaceprune-helper-installer`。
安装器仅接受固定组件集合，不接受任意命令、目标路径或策略文本。通过系统认证后，加锁、复制并复核摘要，
再原子替换整套安装目录；复制过程中不执行来源文件。旧协议目录（包括 `native-6-3`）及旧版单文件安装保留，只用于识别旧安装，不执行其中的组件。
CLI/Desktop 包不各自覆盖共享安装，卸载某个宿主也不删除另一宿主需要的组件。

Desktop 与交互式 CLI 在确实需要权限时自动准备组件。组件缺失、协议或语言入口过期、随包程序摘要变化、
配套 policy 过期时，通过系统授权安装当前应用携带的版本，然后在同次操作中继续检查或执行已确认计划，无需升级引导。
图形只读扫描需要准备组件时，安装器完成验证后直接转入固定 metadata 会话，保留原管道、进程与调用者身份；
安装与首次读取共用这一次认证，不再紧接着启动第二个 pkexec。后续目录和扫描继续复用活连接。
已经一致时不重复安装；普通可读位置不触发安装，非交互任务只使用已经可用的组件。
准备与后续操作共享原取消信号和期限；拒绝或取消不循环重试。设置页和 CLI 安装命令保留为维护入口。
终端“需要授权”提示只在确实启动系统认证时输出；组件检查失败、已有 sudo 认证或复用存活连接不会重复显示密码提示说明。
固定 polkit 策略为读取与清理两种独立能力及其语言入口使用系统 `auth_admin_keep`，没有全局免密规则。
单独执行安装命令只准备组件，不建立扫描连接。安装并读取入口仅能接入 metadata；
清理仍通过独立 action 申请，读取连接不能执行删除。
清理确认集合、目录身份检查、回执、重放拒绝与操作期限仍由清理协议校验，宿主 GUI/CLI 不再作为提权程序。
使用自定义 Cargo target 目录时应替换上述产物路径。

Windows 已接入公共 metadata 服务和独立 cleanup helper；签名安装、UAC、跨账号和原生文件系统验证仍未完成。
macOS 已接入原进程中的隐私恢复，并新增公共 ServiceManagement 注册基础：13+ 走 SMAppService，旧系统走 SMJobBless，注册状态与文件能力严格分开。
macOS 管理员 metadata 与 filesystem cleanup 服务已完成代码接线：签名授权进程直接向固定用途服务交接凭证，宿主不持有凭证；逐请求复核应用与系统管理员 right，保留已有 OS 策略，真实进程签名/audit token 验证与 Mach 大结果传输已接入。同步 OS 权限检查与实际文件工作使用独立执行进程，取消/超时会回收进程并确认停止。清理每次只派发一个已确认项目，宿主保存逐项结果并确认后才允许下一项，进度连续传回。打包、签名/公证脚本及可信旧服务的一次自动更新已接线，见 [macOS 打包指南](../build/MACOS-PACKAGING.md)；CLI 文本授权已接入系统 security 与签名代理，密码只由系统工具读取；真实签名安装/取消及文本认证验收仍未完成，不能仅凭注册或交叉检查宣称可用，也不能把 root 等同 FDA/TCC 许可。
macOS filesystem 的 `elevation = "auto"` 在普通删除出现 EACCES 后选择原生清理服务，`never` 禁止重试，显式 `native` 也选择同一入口。EPERM 保留系统策略拒绝，不自动尝试提权绕过。
三平台原生安装与权限组合验证尚未完成，Linux 测试和 Darwin 目标检查不替代目标系统运行证据。

## 进程内存维护

内存插件使用同一 `builtin.memory` 标识，Windows 与 Linux 在各自的原生适配器中实现。Linux 读取 `/proc` 的内存统计，只列出当前用户可检查的非特权进程；明确选择进程后，才请求系统授权并使用 `process_madvise(MADV_PAGEOUT)`。它不终止进程、不删除数据，也不使用全局 `drop_caches`。

所选身份包含 PID、系统启动标识和进程启动时间，并用 pidfd 绑定真实进程。授权 worker 验证调用用户后放弃 root 身份，只保留页回收所需的 `CAP_SYS_NICE`，让内核继续检查目标访问权限。宿主关闭或取消会关闭请求管道，worker 在下一处理块停止；原操作期限保持有效。部分效果按进程报告，驻留内存的观测减少量不等于系统新增空闲 RAM，也不计入磁盘清理空间。后续访问可能重新加载页面。

### 可重复使用的内存规则

`builtin.memory/process-working-set` 支持 Windows、Linux。`options.applications` 填写完整可执行文件路径，不填程序简称或 PID。每次扫描重新发现当前用户的进程；执行前绑定并复核本次选中的 PID、启动身份及可执行文件路径。执行前已退出的进程自动跳过，新增释放量记为零；身份或可执行文件已改变则拒绝操作，不改为操作其他进程。部分释放后发生退出仍保留部分作用回执。程序未运行时没有可选项。已有手动 PID／启动身份接口继续可用。

```toml
[modules.memory]
name = "应用内存"

[modules.memory.tasks.editor]
name = "编辑器工作集"
handler = "builtin.memory/process-working-set"
platforms = ["linux"]
options.applications = ["/opt/editor/editor"]
recommend.enabled = true
```

填写检查结果中的实际程序路径。Windows 使用 TOML 字面字符串，例如 `'C:\Program Files\Editor\editor.exe'`，并设置 `platforms = ["windows"]`。路径区分的是可执行程序，不是共享解释器中运行的每个应用，例如多个 Node 应用使用同一个 `node` 可执行文件；只想整理其中一个应用时，不要选择共享解释器路径。

内存使用独立计量类型 `memory_bytes`。扫描显示驻留工作集，执行结果单独报告观测到的减少量、部分效果和未测得项，不混入磁盘估算。Linux 后台计划仅使用已有权限，无授权时报告失败而不弹窗；Windows 使用当前用户已有进程权限，不调用管理员组件。Linux 规则执行要求支持可执行路径绑定的新 helper，旧组件会被拒绝，不会静默跳过核验。

Windows 适配器已交叉编译；带完整路径的规则仍需 Windows 打包／原生验收。隔离测试覆盖失效身份和伪造选择，不对真实用户进程执行内存维护。
