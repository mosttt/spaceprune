# Local permissions and authorization reuse

Scanning starts with current-user permissions. Only when ordinary files, system caches, Snapper listings, or their size measurements encounter insufficient permissions does the shared Linux access service request read-only authorization. System-cache retries retain package-cache, coredump, and Go paths discovered as the ordinary user; they do not rerun Go environment discovery as administrator. Go paths are passed as native bytes. After authorization recovery, directory and parent identities are bound; measurements crossing links or nested mounts are not considered complete. Subsequent checks reuse a live helper connection, validating origin, scope, protocol version, expiry, and a one-time nonce for every request. Read permission is not deletion confirmation.

If a Snapper list command fails, `GetConfig` (for a specific configuration) or `ListConfigs` on the fixed system bus checks the actual access result. Authorization is requested only from structured service permission-error names or native I/O errors, not inferred from English error text. Diagnostics take at most 5 seconds and inherit the original cancellation/deadline. Missing configurations, unavailable services, or custom programs printing permission-related text do not trigger authorization based on text alone. Successful listings, protection state, and cleanup selection retain their original semantics.

Graphical hosts use the system authorization dialog. Terminals first reuse sudo authentication; sudo prompts only when needed. SpacePrune does not store or receive passwords.

On Linux, the scan prompt says “Allow SpacePrune to read file information in protected locations to complete the scan. No files will be deleted.” The cleanup prompt says “Allow SpacePrune to clean the protected items you have selected and confirmed.” These purpose messages follow the effective CLI / App language: a manual choice overrides the system language, Simplified Chinese and English are supported, and other languages fall back to English. Dialog titles, password labels, and buttons remain translated by the system authentication agent. During initial component installation or an update, the system may first display its generic installation prompt; Settings retains localized component-installation guidance. Automatic preparation then continues reading without a second prompt.

Noninteractive runs use only existing connections or OS-permitted noninteractive authentication; when unavailable, readable scan results are retained and authorization is reported as needed. An explicit refusal suppresses further prompts within that operation, even across directories or Snapper configurations. A new operation may request authorization again. Connections expire after 15 idle minutes or process exit.

Reuse is bound to the local OS login identity, not merely a username or UID. Foreground and terminal bindings are permanently revoked for that operation when the user switches away, logs out, or the login service fails: in-flight privileged requests are cancelled, native connections are awaited until stopped, and the old operation ID/generation cannot reauthorize. A login already shutting down also revokes reuse without waiting for every remaining process to exit. Switching back does not revive the old operation; a new operation revalidates login state and requests permission as needed. Ordinary unprivileged file scans do not thereby require a graphical login. A close failure retains its initial result; removal from the connection cache does not turn failure into success.

Independent noninteractive tasks retain their original operating conditions. When the OS identifies a login session, they bind to it and monitor logout, but do not stop solely on GUI switching; they use only their existing noninteractive capabilities. An existing foreground binding cannot be downgraded by changing a caller to NonInteractive. Moving a background binding to an interactive request first closes the old connection and rechecks foreground state. Environments confirmed by the OS to have no login session or login service use process scope; a known login-monitor failure does not silently downgrade. Linux queries logind on the trusted system bus. Foreground user-manager applications can associate a same-UID `User.Display` session without trusting `XDG_SESSION_ID` or `DBUS_*` identity hints.

Linux read-only and cleanup are separate components, providing metadata and execution of confirmed cleanup plans respectively. Their startup protocols are not interchangeable. CLI and Desktop share `/usr/libexec/spaceprune/native-6-4`, managed by the Core installer; the numbers denote read protocol 6 and cleanup protocol 4. Files and the full directory chain must be root-owned and not writable by ordinary users. Before startup, manifest SHA-256, role protocol, and the built-in handler contract are checked. Matching transport protocols do not establish handler compatibility: a component still using the old Snapper identifier is neither reported ready nor reinstalled.

The native Go-capture feature probe applies only to Go-worker lookup and actual elevated Go batches. Snapper, ordinary files and system-cache operations retain their original protocol requirements. Go already completed by an ordinary worker, or never requesting elevation, does not impose a new requirement on other batches. If an existing basic session later needs Go support, matching components are prepared before the old connection is closed; the replacement starts only after shutdown is confirmed. Consumed selections, the original operation deadline and authorization caching survive the replacement. A missing Go bundle does not block later Snapper batches, and old helpers never receive Go selections.

```sh
cargo build --locked --release -p spaceprune-cli -p spaceprune-readonly-helper
./target/release/spaceprune authorization install
```

Distributions include adjacent `spaceprune-readonly-helper`, `spaceprune-cleanup-helper`, and `spaceprune-helper-installer`. The installer accepts only the fixed component set, not arbitrary commands, target paths, or policy text. After system authentication, it locks, copies, verifies digests, and atomically replaces the complete installation directory. Source files are not executed during copying. Older protocol directories, including `native-6-3`, and old single-file installations are retained only to identify old installations; their components are not executed. CLI/Desktop packages do not independently overwrite the shared installation, and removing one host does not delete components another host needs.

Desktop and interactive CLI prepare components automatically when permission is actually needed. If components are missing, protocol-outdated, differ from bundled program digests, or have outdated prompt entrypoints or policy, system authorization installs the version carried by the current application, then continues the check or confirmed cleanup within the same operation, without upgrade guidance. When a graphical read-only scan needs preparation, the installer validates and transitions directly into the fixed metadata session, retaining the original pipes, process, and caller identity. Installation and first read share that authentication rather than immediately starting a second pkexec. Later directories and scans reuse the live connection.

Matching components are not reinstalled; ordinary readable locations do not trigger installation, and noninteractive tasks use only components already available. Preparation and subsequent work share the original cancellation signal and deadline; refusals or cancellations do not cause retry loops. Settings and the CLI install command remain maintenance entry points. The terminal authorization notice appears only when system authentication actually starts; component-check failures, existing sudo authentication, and live-connection reuse do not repeat password instructions.

The fixed polkit policy uses system `auth_admin_keep` for separate read and cleanup capabilities and their language entrypoints, with no global passwordless rule. Running the installation command alone prepares components without opening a scan connection. Install-and-read connects only to metadata; cleanup requests its separate action, and read connections cannot delete. The cleanup protocol still validates the confirmed selection, directory identity, receipts, replay rejection, and operation deadline. The host GUI/CLI is no longer the elevated program. Adjust the artifact paths above when using a custom Cargo target directory.

Windows integrates the shared metadata service and separate cleanup helper; signed installation, UAC, cross-account behavior, and native filesystem acceptance remain incomplete.

macOS integrates in-process privacy recovery and shared ServiceManagement registration: 13+ uses SMAppService, older versions use SMJobBless. Registration state is strictly separate from file capabilities. Administrator metadata and filesystem cleanup services are wired: a signed authorization process hands credentials directly to fixed-purpose services, without the host holding them. Requests revalidate the app and OS administrator right, retain existing OS policy, and use actual process-signature/audit-token verification and Mach transport for large results. Synchronous OS permission checks and actual file work run in separate worker processes; cancellation/timeouts reclaim them and confirm they have stopped. Cleanup dispatches one confirmed item at a time; the host saves and acknowledges its result before allowing the next, with continuous progress updates. Packaging, signing/notarization scripts, and one automatic update of trusted older services are wired; see [macOS packaging](../build/MACOS-PACKAGING.md). CLI text authorization uses system `security` and a signed agent; only the system tool reads passwords. Real signed installation/cancellation and text authentication acceptance remain incomplete. Registration or cross-checks alone do not establish usability, and root access is not FDA/TCC permission.

For macOS filesystems, `elevation = "auto"` selects the native cleanup service after ordinary deletion encounters EACCES; `never` prohibits retries, and explicit `native` uses the same entry point. EPERM remains an OS policy denial and does not automatically trigger elevation to bypass it.

Combined native installation and permission acceptance across all three platforms remains incomplete. Linux tests and Darwin target checks do not replace runtime evidence from each target system.

## Manual Linux process-memory maintenance

The memory plugin keeps one `builtin.memory` identity, with native Windows and Linux adapters. Linux reads `/proc` statistics and lists inspectable, unprivileged current-user processes. Only an explicit process selection requests authorization and invokes `process_madvise(MADV_PAGEOUT)`. It does not terminate processes, delete data, or use global `drop_caches`.

Selections bind the PID, boot identity and process start time, with a pidfd retaining the actual process. The authorized worker verifies the caller, drops its root identity and retains only `CAP_SYS_NICE`, so the kernel continues enforcing target-access checks. Host cancellation or exit closes the request pipe; the worker stops at the next chunk, under the original deadline. Partial effects are reported per process. Observed resident-memory reductions are not additional system-wide free RAM or disk-cleanup savings; subsequent access may reload pages.
